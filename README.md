# TeX-memory: Reimplementations of TeX's memory management in C++

The rationale and purpose of this repo are described in the series
of posts beginning with the one titled [Reading "TeX: The Program" in 2026](https://kirkpatricktech.org/2026/09/03/reading-tex-the-program/).
This README complements that series by describing the layout of the code
and the mechanics of building and running the tests and benchmarks.

## Layout of the code

The two main directories are:

* <code>original-approach</code>: Reimplementation of the TeX
  memory management in C++. The algorithms and code closely match
  the original WEB/Pascal. In particular, no C++ memory management,
  such as <code>new</code> or <code>delete</code> are used.
* <code>modern-approach</code>: Reimplementation of the TeX
  type hierarchy using C++ classes and dynamic memory management.
  This version uses all the pertinent features of C++&nbsp;23.

In addition, there are two support directories:

* <code>include</code>: All header-only external dependencies. Currently,
  this only contains the header for Catch2 v2.
* <code>common</code>: Test and benchmarking harness routines
  common to both the original and modern approaches. The code
  in these routines has no counterpart in TeX.

Finally, there are miscellaneous files:

* Container-related: The files <code>build-image.sh</code>, <code>run.sh</code>
  and <code>Dockerfile</code>, used manage the container
  in which the tests are built and run. Further details below.
* Benchmark-related: The files <code>benchmarks.csv</code>
  and <code>parse-benchmarks.py</code>, which process and
  store benchmark data. Further details below.

## Building and running the environment for the tests

The tests are designed to be built and run in a container
based on Ubuntu&nbsp;25.10, also including gcc&nbsp;15.2,
gdb&nbsp;16.3, and Python&nbsp;3.13.
The contents are defined in <code>Dockerfile</code>,
while the simple bash scripts <code>build-image.sh</code>
and <code>run.sh</code> build and run the container.

## Building and testing the code

In the running container, build the code by running <code>make</code> in each
directory:

<pre>
cd common
make all
cd ../original-approach
make test
cd ../modern-approach
make test
</pre>

The latter two commands will run unit tests on the code
after it is built. The <code>original-approach</code> has
detailed testing while the <code>modern-approach</code>
has only a single test.

### Special builds to analyze the code

Two special builds support more detailed code analysis.
First, if you set the variable <code>COV</code> and rebuild
the system, you can run coverage tests using [gcovr](https://gcovr.com/en/stable/):

<pre>
/usr/code/src/original-approach# make clean
... deletions listed ...
/usr/code/src/original-approach# make COV=yes all
... output of compiles
/usr/code/src/original-approach# make test
... test output ...
/usr/code/src/original-approach# source ../../venv/bin/activate
/usr/code/src/original-approach# gcovr .
</pre>

Some notes:

* Compiling with the <code>COV=yes</code> option takes an order
  of magnitude more time than regular compiles. This is largely due
  to my poor configuration of the options, which
  insert coverage code for every dependency, not just the code
  in this repo.
* The <code>gcovr</code> app is written in Python and located in
  the Python virtual environment <code>/usr/code/venv</code>.
* Take care to rebuild the entire system *without* the <code>COV</code>
  option before running any benchmarks.

Second, if you want to see the machine code generated by a given
compile of a file, make the <code>.s</code> target of that file:

<pre>
make box_classes.s # Machine code for box_classes.cpp
</pre>

## Running a benchmark

To run a benchmark of either approach, switch to the
appropriate directory and make the <code>benchmark</code>
target:

<pre>
cd original-approach # or modern-approach
make TRAVERSALS=<I>n</i> OPT_LEVEL=<i>opt</i> benchmark
</pre>

where

* *n* is the number of traversals to perform in the 
  build/traverse/destroy benchmark. See the benchmark results
  in the posts linked above for more details.
* *opt* is a gcc optimization argument, such as <code>-O1</code>.

The make will force a recompile of all files in the current
directory (but not in <code>common</code>) using the specified
optimization argument, rebuild the test and benchmark executables,
run the test(s), andrun the benchmark with the specified
traversal count to generate an XML file, and finally
run <code>parse-benchmarks.py</code> to parse the XML.
The benchmark results, including the traversal and
optimization arguments, will be stored as lines appended to
the file <code>../benchmarks.csv</code>.

### Running a benchmark without rebuilding the system

If you want to run several benchmarks in a row, say with different
traversal counts, it is tedious and unnecessary to rebuild the
entire system every time. Look at the <code>Makefile</code> to
see how to just run the benchmark alone. But if you make
any changes to the source code, it is safest to rebuild
everything, so that the optimization level is consistent.

## Analyzing the results

Analyze your benchmark results by loading <code>benchmarks.csv</code>
into your preferred analysis tool.
